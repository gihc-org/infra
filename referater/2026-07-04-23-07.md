# Sessionsreferat 2026-07-04 (del 2)

Fortsættelse fra referat `2026-07-04-12-00.md`.

## Hvad blev lavet

**Diskussion om deklarativ k3s-opsætning** — inden `tofu apply` blev kørt på den
ryddede infrastruktur, blev to designproblemer i det eksisterende setup
identificeret:
- `k3s_install_script` lå i `hcloud_server.platform`'s `user_data` (cloud-init),
  som kun kører én gang ved boot. Kombineret med `ignore_changes = [user_data]`
  betød det at ændringer i scriptet aldrig ville slå igennem på en eksisterende
  server — reelt udeklarativt trods Terraform-syntaksen.
- `ansible/infra.yml` installerede slet ikke k3s længere (kun post-provisionering:
  vente, hente kubeconfig, verificere) — en drift fra den oprindelige lag-beslutning
  fra 29/6, hvor Ansible skulle eje k3s-installationen.

Afklaret undervejs: `/etc/rancher/k3s/`-stien og `system-upgrade-controller` er
opkaldt efter Rancher Labs (k3s' ophavsmand), men kræver ikke og installerer ikke
den fulde Rancher management-platform.

**Refaktorering gennemført:**
- `tofu/main.tf`: fjernet `k3s_install_script`-locals og `user_data` fra
  `hcloud_server.platform`. Tofu opretter nu kun den bare VPS.
- `tofu/variables.tf` + `terraform.tfvars.example`: fjernet `k3s_version`
  (hører nu til i Ansible).
- `ansible/templates/k3s-config.yaml.j2` (ny fil): deklarativ k3s-config
  (`disable traefik`, `flannel-iface`, `node-ip`, `tls-san`) i stedet for
  CLI-flags i et bash-script — dette er den konfigurationsmekanisme k3s selv
  tilbyder.
- `ansible/infra.yml`: nye tasks forrest i playbooken — opret
  `/etc/rancher/k3s`, templat `config.yaml`, kør install-scriptet med
  `INSTALL_K3S_VERSION` fra variablen. Scriptet er idempotent og opgraderer
  et eksisterende k3s in-place, så opgradering fremover er: bump
  `k3s_version` i `group_vars`, genkør playbooken.
- `ansible/inventory.yml`: tilføjet `k3s_node_ip: 10.0.1.1` (host-var, matcher
  den faste private IP fra `main.tf`).
- `ansible/group_vars/all/vars.yml`: tilføjet `k3s_version: latest`.
- `README.md` og `TODO.md` opdateret til at afspejle at Ansible nu ejer hele
  k3s-livscyklussen.

**Udførelse — fra tom Hetzner-konto til kørende cluster:**
1. `tofu plan` fejlede først med `token_readonly` / `forbidden` — Hetzner
   API-tokenet var Read Only. Nyt token med Read & Write oprettet og gemt i
   `pass hetzner/token`.
2. `tofu apply` kørt: 6 ressourcer oprettet (SSH-nøgle, netværk, subnet,
   server, firewall, firewall-attachment), 0 destroy. Samme public IP som før
   (65.109.233.92).
3. Ansible installeret lokalt via `uv`. `uv tool install ansible` viste sig
   kun at eksponere `ansible-community` (ikk `ansible-playbook`) fordi uv kun
   linker entry points fra selve den pakke man beder om, ikke fra
   afhængigheder. Løst med `uv tool install ansible-core` direkte, som
   eksponerer `ansible-playbook`, `ansible-galaxy` m.fl.
4. Playbook-kørsel fejlede først på `Host key verification failed` /
   `ssh_askpass` — `ansible.cfg` (med `host_key_checking = False`) blev ikke
   fundet, fordi Ansible kun leder efter config i CWD, og playbooken blev
   kørt fra repo-roden mens filen lå i `ansible/ansible.cfg`.
5. Næste fejl: `Permission denied (publickey,password)` — SSH-nøglen
   (`~/.ssh/id_ed25519.hetzner`) har en passphrase og kunne ikke bruges
   non-interaktivt. Løst ved at brugeren selv kørte `ssh-add`.
6. k3s-service fejlede ved opstart: `unable to find interface eth1: route
   ip+net: no such network interface`. Root cause: Ubuntu 24.04 bruger
   predictable network interface naming — det private interface hedder
   `enp7s0`, ikke `eth1`. Samme fejl lå skjult i det oprindelige
   cloud-init-script og var aldrig blevet testet før denne session.
   `k3s-config.yaml.j2` rettet til `enp7s0`.
7. Efter rettelsen: k3s startede korrekt, node blev `Ready` med korrekt privat
   IP (10.0.1.1) som internal-IP. Playbookens eget node-tjek (`kubectl get
   nodes`) ramte dog et race condition (tjekkede før node-objektet var
   registreret) — rettet med `retries`/`delay`/`until` på tasken.
8. Til sidst flyttet `ansible/ansible.cfg` → `ansible.cfg` i repo-roden, så
   den altid findes når playbooken køres fra roden (som README foreskriver),
   uden at skulle sætte `ANSIBLE_CONFIG` manuelt.

## Beslutninger

**k3s-installation og -opgradering ejes af Ansible, ikke Tofu.** Tofu
opretter kun cloud-ressourcer (server, netværk, firewall, SSH-nøgle).
Begrundelse: `user_data` er et engangs-boot-script og kan ikke bruges til
løbende livscyklus-styring; det matcher desuden den oprindelige
lag-beslutning fra 29/6 (Tofu = cloud, Ansible = k3s, Helm = platform).

**k3s-konfiguration lever i `/etc/rancher/k3s/config.yaml`**, templated af
Ansible, i stedet for CLI-flags i et install-script. Det er k3s' egen
deklarative konfigurationsmekanisme og overlever genkørsler/opgraderinger
uden at flags skal huskes eller gentages.

**`system-upgrade-controller` fravalgt** — vurderet som overkill til et
enkelt-node hobby-cluster; Ansible-genkørsel med versionsbump er tilstrækkeligt
og enklere.

**`ansible.cfg` skal ligge i repo-roden**, ikke i `ansible/`-undermappen —
Ansible leder kun efter config i CWD, og README's dokumenterede
kørselsmåde (`ansible-playbook ansible/infra.yml -i ansible/inventory.yml`
fra repo-roden) forudsætter det.

## Gotchas

- **`ignore_changes` på `user_data` maskerer drift permanent** — selv uden
  det ville en `user_data`-ændring kun tage effekt ved server-genskabelse
  (destroy/recreate), da cloud-init kun kører ved første boot.
- **`uv tool install <pakke>` eksponerer kun entry points fra selve pakken**,
  ikke fra dens afhængigheder. `ansible`-pakken (community) afhænger af
  `ansible-core` (hvor `ansible-playbook` bor) — installer `ansible-core`
  direkte hvis man kun skal bruge `ansible.builtin.*`-moduler.
- **Ansible finder kun `ansible.cfg` i CWD** (eller via `ANSIBLE_CONFIG`),
  ikke relativt til playbook-filens placering.
- **SSH-nøgler med passphrase kræver `ssh-agent`** for non-interaktiv brug
  (Ansible, cron, CI) — `ssh_askpass`-fejlen er symptomet når det mangler.
- **Ubuntu 24.04 bruger predictable network interface naming** — Hetzners
  private netværksinterface hedder `enp7s0` på denne server/image-kombination,
  ikke `eth1`. Kan i teorien ændre sig ved skift af `server_type` eller image;
  verificér med `ip -brief addr` hvis k3s fejler med "unable to find interface".
- **`wait_for` på k3s API-port 6443 garanterer ikke at node-objektet er
  registreret** — kort race condition mellem API'en svarer og
  `kubectl get nodes` viser noden som `Ready`. Løst med retry-loop.
